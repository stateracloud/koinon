# Domain Docs

How the engineering skills should consume Koinon's domain documentation when exploring the codebase.
Koinon is single-context: one `GLOSSARY.md` at the repo root and the decisions in `docs/adr/`.

## Before exploring, read these

- **`GLOSSARY.md`** at the repo root.
- **`docs/adr/`**: read the ADRs that touch the area you're about to work in. ADRs are canonical;
  `docs/design.md` is the overview and indexes them by topic. The ADR index (`docs/adr/README.md`) is
  generated by `hack/adr-index.sh`; reserve a new ADR number with `hack/claim.sh adr`.

If any of these files don't exist, **proceed silently**. Don't flag their absence; don't suggest
creating them upfront. The `/domain-modeling` skill (reached via `/grill-with-docs` and
`/improve-codebase-architecture`) creates them lazily when terms or decisions actually get resolved.

## File structure

```
/
├── GLOSSARY.md
├── docs/design.md          ← overview, indexes the ADRs
├── docs/adr/
│   ├── README.md           ← generated index
│   ├── 0001-….md
│   └── …
└── internal/, cmd/, web/, charts/ …
```

## Use the glossary's vocabulary

When your output names a domain concept (in an issue title, a refactor proposal, a hypothesis, a
test name), use the term as defined in `GLOSSARY.md`. Don't drift to synonyms the glossary
explicitly avoids.

If the concept you need isn't in the glossary yet, that's a signal: either you're inventing language
the project doesn't use (reconsider) or there's a real gap (note it for `/domain-modeling`).

## Flag ADR conflicts

If your output contradicts an existing ADR, surface it explicitly rather than silently overriding:

> _Contradicts ADR-0007 (…), but worth reopening because…_

A change to a decision in an ADR goes in as a dated amendment section of that ADR (or a new ADR),
never as a silent edit.
